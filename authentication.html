Authentication

Quick refresher

Authentication establishes confidence in the identity of a person or workload. A credential proves something at sign-in. A session preserves continuity across requests. Federation delegates sign-in to a trusted identity provider.

Worked example

An employee opens an internal expense app. The app starts an OpenID Connect authorization code flow with PKCE. After the identity provider authenticates the employee, the app exchanges the code and validates the ID token before creating an application session.

Continue to Access Controls

Protocol and token roles

OAuth provides delegated authorization. OpenID Connect adds an identity layer. An ID token carries authentication claims for the client. An access token is presented to the intended resource server. Validate issuer, audience, expiry, and the expected signature using a vetted library. Bind the login flow to the initiating browser using the protocol's state and nonce protections as applicable.

Authenticator choices

Compare passwords, one-time codes, and passkeys across phishing resistance, deployment, device loss, and recovery. WebAuthn credentials are scoped to a relying party and use public-key authentication. Protect enrollment and recovery because those paths can determine the account's effective assurance.

Session lifecycle

For a browser-based app, use a random session identifier in a cookie with Secure, HttpOnly, and an appropriate SameSite policy. Rotate it after sign-in or privilege changes, apply expiration, and invalidate server-side sessions on logout or offboarding where required. Keep CSRF protection consistent with the cookie strategy.

Verification

Test expired credentials, mismatched issuer or audience, session expiration, reauthentication for sensitive actions, logout, and account recovery. Record sign-in outcomes and administrative changes without logging credentials or tokens.

Interview practice

How would you design sign-in and offboarding for an internal expense app?

Use the organization's identity provider with phishing-resistant MFA where appropriate. Establish an application session after validating the sign-in result. On departure, disable the identity and revoke relevant app sessions and tokens. Verify how quickly each layer reflects the departure.

Does disabling a user at the identity provider immediately end every app session?

It depends on session and token design. A locally validated token may remain usable until expiry. An application session may persist until invalidation or a fresh policy check. Set a revocation target and test it end to end.
